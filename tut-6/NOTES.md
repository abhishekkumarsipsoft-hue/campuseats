### A2 — Responses that returned 200 for a failure
We audited every response. No handler ever returned `200 {"ok": false}`. Two A5 responses were still
dishonest, and both are fixed:

| A5 behaviour | Why it was dishonest | A6 behaviour |
|---|---|---|
| Payments unreachable → **`202 Accepted`** with `refund_status: "failed_pending_retry"`, order left stuck in `cancelling` | The cancel *failed*, but the status line said "accepted". Nothing ever retried it. | **`503`** + `Retry-After`; order restored to its previous status; safe to retry. |

## Part B — One error shape

### B1 — Everything goes through `problem()`
`errors.problem(slug, detail, errors=None, headers=None)` is the only way a failure response is built. That includes
failures we do not write handlers for: `@app.errorhandler(HTTPException)` routes Flask's own 404/405 through it and
`@app.errorhandler(Exception)` routes any uncaught exception through it. Errors are always
`application/problem+json`, whatever the `Accept` header says.

### B2 — Type catalogue
See **Answer 2**. Slugs are defined once, in `errors.CATALOGUE`, together with their status — a slug cannot be sent
with two different statuses. (A5 derived the slug from the title text, so rewording a title silently changed the type.)

### B3 — Field-level 422
`errors[]` of `{field, message}`; see **Answer 4**.

### B4 — No internals
See **Answer 6**.

## Part C — Request validation & formats

### C1 — The body, described
`openapi.yaml` → `OrderCreateRequest`: `items` non-empty array; each item `name` (non-empty string), `price_cents`
(integer ≥ 0), `qty` (integer ≥ 1); `customer_id` and `address` required non-empty strings. `validation.validate_create_order`
enforces exactly that. JSON `true`/`false` is **not** accepted as an integer (in Python `True` is an `int`, so a naive
`isinstance(x, int)` lets `qty: true` through).

### C2 — Validate, then act
`create_order` validates everything first and collects **every** error
(`test_every_error_is_collected_not_just_the_first` gets five at once), returns one `422`, and only then touches the
store (`test_invalid_work_is_not_done`).

### C3 — Content negotiation
`Accept` defaults to JSON; `application/xml` is produced on request; `q` values and `*/*` are honoured; anything else
is `406 not-acceptable`. See **Answer 7**.

### C4 — Every body labelled
Every response with a body has a `Content-Type` ending `; charset=utf-8`, errors included
(`application/problem+json; charset=utf-8`). Bodyless `204`/`304` carry no `Content-Type`.

## Answers

### 1. Status map — every endpoint, success, and each failure

| Endpoint | Success | Failures (and why) |
|---|---|---|
| `POST /orders` | **201** Created + `Location` — a new resource now exists | **400** `malformed-json` — body missing / not JSON / not an object, can't even be parsed · **401** no Bearer token · **406** can't produce the requested format · **422** parsed fine but invalid: `empty-cart`, `validation-error` (field list) or `item-unavailable` — the *content* is wrong, not the syntax · **429** rate limit · **500** our bug |
| `GET /orders/{id}` | **200** OK + `ETag` · **304** Not Modified — client's copy is current | **404** `order-not-found` · **406** · **429** · **500** |
| `GET /orders?status=` | **200** OK (an empty list is still 200 — "no matches" is not an error) | **406** · **429** · **500** |
| `PATCH /orders/{id}` | **200** OK — returns the updated order | **400** body problems · **401** · **404** · **409** `illegal-transition` — valid request, but the order's *current state* forbids the move (e.g. `preparing → delivered`) · **422** missing/unknown `status` · **406** · **429** · **500** |
| `DELETE /orders/{id}` | **204** No Content — cancelled and refunded, nothing to return | **401** · **404** · **409** `illegal-transition` (already cancelled, out for delivery, delivered) · **402** `payment-declined` — Payments refused the refund · **503** `payments-unavailable` + `Retry-After` — Payments down, order unchanged · **406** · **429** · **500** |
| `POST /orders/{id}/cancellation` | **202** Accepted (cancellation record + refund done; body shows `refund_status`) | same as `DELETE`, plus **412** `precondition-failed` for a stale `If-Match` |
| `OPTIONS /orders/{id}` | **204** | — |

*Why 409 for `illegal-transition`:* nothing is wrong with the request's content; it conflicts with the resource's
current state, and the same request could succeed from a different state. 422 is reserved for requests whose own
content is invalid. *Why 402 for a declined refund:* Payments said "no" definitively — retrying the same request will not
help and it is not our fault (not 5xx).

### 2. Type catalogue

All `type` values are `https://campuseats.example/problems/<slug>`.

| Slug | Status | Triggered by |
|---|---|---|
| `empty-cart` | 422 | `POST /orders` with `items: []` |
| `item-unavailable` | 422 | an order line names an item the catalogue cannot supply (`Sold-Out Samosa` in our stub) |
| `payment-declined` | 402 | Payments answered the refund with a definitive 4xx |
| `order-not-found` | 404 | the `{id}` in the URL matches no order |
| `illegal-transition` | 409 | PATCH to a status the current one can't reach; cancel of a cancelled / out-for-delivery / delivered order |
| `validation-error` | 422 | any other body field failure (carries `errors[]`) |
| `malformed-json` | 400 | body empty, unparseable, not a JSON object, or not sent as JSON |
| `bad-request` | 400 | other protocol-level faults raised by the framework |
| `unauthorized` | 401 | missing/empty Bearer token |
| `not-found` | 404 | URL that is not an Orders route at all |
| `method-not-allowed` | 405 | e.g. `PUT /orders/{id}` |
| `not-acceptable` | 406 | `Accept` names nothing we can produce |
| `precondition-failed` | 412 | `If-Match` doesn't match the current ETag |
| `rate-limit-exceeded` | 429 | too many requests from one client in the window |
| `payments-unavailable` | 503 | Payments unreachable after retries |
| `internal-error` | 500 | any unexpected exception |

### 3. One Problem Details body, labelled
From `transcript.txt` entry 8 (`GET /orders/does-not-exist-id`):
```
HTTP/1.1 404 NOT FOUND
Content-Type: application/problem+json; charset=utf-8

{"detail":"No order with id does-not-exist-id.","status":404,"title":"Order Not Found","type":"https://campuseats.example/problems/order-not-found"}
```
| Field | Meaning |
|---|---|
| `type` | stable, machine-readable identifier of the *kind* of failure — what a client's code switches on |
| `title` | short human-readable name for that kind; identical every time |
| `status` | the HTTP status, repeated in the body so the body is self-describing if logged or forwarded |
| `detail` | explanation of *this* occurrence (names the id that was not found) |
| `errors[]` | only on field-level 422s — see next answer |

### 5. Which endpoints are safe to retry, and which statuses say so?
**Rule:** retry only *transient* failures; never resend a 4xx unchanged, because the same request fails the same way.

| Signal | Meaning for the client |
|---|---|
| `429` + `Retry-After` | retry the **same** request after that many seconds |
| `503` + `Retry-After` | retry the **same** request after that many seconds (Payments was down; the order was left unchanged) |
| connection error / timeout, no response | retry — subject to the per-endpoint rule below |
| any other `4xx` (400, 401, 402, 404, 406, 409, 412, 422) | **do not** retry unchanged; fix the request, re-read the resource, or give up |
| `500` | not marked retryable by us |

| Endpoint | Retry-safe? |
|---|---|
| `GET /orders`, `GET /orders/{id}`, `OPTIONS` | **Yes, always** — safe and idempotent |
| `POST /orders` | **Only with an `Idempotency-Key`.** Same key returns the original order (same id), so a retry after a lost response cannot create a duplicate. |
| `PATCH /orders/{id}` | Effectively yes: replaying `{"status":"preparing"}` after it succeeded gives `409 illegal-transition`, telling the client the move already happened. Nothing is applied twice. |
| `DELETE /orders/{id}` and `POST …/cancellation` | **Yes.** A `503` leaves the order unchanged and the refund call carries an `Idempotency-Key` (`cancel-{id}` by default), so Payments cannot refund twice; retrying after success gives `409` rather than a second refund. A `402` is *not* retryable. |

### 6. Where did we map an internal error to a clean client error, and what was hidden?
| Internal event | Client sees | Hidden (logged server-side only) |
|---|---|---|
| `PaymentsUnavailable` — Payments unreachable after 4 attempts | `503 payments-unavailable`, `Retry-After: 30` | the Payments URL/host, the underlying `ConnectionError`/timeout text, the retry count |
| `PaymentsRejected` — Payments answered 4xx | `402 payment-declined`, generic sentence | Payments' raw response body (A5 pasted it into `detail`) and its status code |
| any unexpected exception | `500 internal-error` + a short **reference id** | the stack trace and exception message, logged by `log.exception` with the same reference id |
| Flask/Werkzeug HTTP errors (unknown URL, wrong method) | `404` / `405` Problem Details | Werkzeug's HTML page and its wording |

In every refund-failure path the order is put back to its previous status before responding, so a failure never leaves an
order stuck in `cancelling`. Proof: `test_refund_declined_402_and_order_is_unchanged`,
`test_payments_down_503_with_retry_after_then_retry_works`, and `test_unexpected_exception_is_mapped_to_clean_500`
(raises `RuntimeError("psycopg2.OperationalError: password=hunter2 host=db.internal")` and asserts none of it reaches the client).

### What changed since A5, and why (all covered by tests)
- `PATCH` and `DELETE` on `/orders/{id}` added (the brief's status map lists them). `PATCH` also makes `illegal-transition`
  demonstrable through the API — in A5 no endpoint could move an order to `delivered`, so the domain refusal could only be
  produced by editing the store directly.
- `address` is now required on create (C1).
- Domain refusals that A5 reported as `422 Cancellation Not Allowed` / `409 Order Already Cancelled` are one type now:
  `409 illegal-transition`.
- Payments failures are `402` / `503` instead of a raw-body `422` / a `202` (see A2, Answer 6).
- Non-JSON / non-object bodies are a clean `400` (a list body on the cancellation route is ignored rather than crashing).

### Known limitations (stated, not hidden)
- Storage is in-memory; state is lost on restart. Auth checks header shape only (no verification, no per-user ownership).
- `GET /orders` and `GET /orders/{id}` are unauthenticated, as in A4/A5 (`security: []` in the spec).
- `item-unavailable` is checked against a hard-coded set standing in for the Catalogue service.
- Inherited from A5 and deliberately left alone in this assignment: `X-HTTP-Method-Override` is applied in a
  `before_request` hook, which runs after Flask has chosen the route, so it does not change which handler runs; the
  explicit `OPTIONS` handler is shadowed by Flask's automatic one; the rate limiter keys on the (unverified) `Authorization`
  header, and idempotency keys are not scoped per caller.
